# Phase 3.2 — development authentication
1. Export a local backup. Deploy the updated web files to the existing GitHub Pages origin. Do not publish tests or SQL folders.
2. In Supabase Authentication, enable Email provider and email confirmations. Set minimum password length to at least 8. Under URL Configuration set Site URL and allowed redirect URLs to the exact deployed DailyForm page (including index.html if used). The app uses the current origin and pathname. Keep redirects narrowly scoped. Default email templates must use the confirmation URL (implicit token flow); custom PKCE templates are not supported in this build.
3. No new SQL is required. Keep the foundation documents table inaccessible to both anon and authenticated roles. No fitness data is synced. Test with synthetic accounts and records only.
4. Close old PWA windows, reopen, and find Settings > DailyForm account. Register, confirm email, sign in, save display name, reload, sign out, and test password recovery. Test guest and offline use. Test two accounts; local fitness records are intentionally device-wide, not account isolated. Do not use shared devices for private data.
5. Verify database permissions using SQL editor: select grantee, privilege_type from information_schema.role_table_grants where table_schema='public' and table_name='dailyform_documents' and grantee in ('anon','authenticated','PUBLIC'); expected zero rows. This is not a full security audit.
Limitations: browser localStorage stores session tokens; no production security audit, cross-tab refresh coordination, or proactive token refresh. Tokens refresh when an account operation requires it. Offline session display is not proof of current authentication. Supabase default email delivery may restrict recipients/rate; configure SMTP before broader testing. No live auth or browser testing performed in this build.
